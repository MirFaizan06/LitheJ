Result & Error Handling

LitheJ uses two complementary tools for failure, and is deliberate about which one applies where.

Exceptions, for genuine failures

A missing file, a malformed number, a network error — these are exceptions, mostly unchecked, and every method's Javadoc documents exactly what it throws and why. This is ordinary Java; LitheJ does not invent a new convention here.

Result<T, E>, for expected outcomes

Use lithej.core.Result when a "failure" is a normal, recoverable outcome you want to handle without exception-based control flow — e.g. "the input didn't parse," "the API returned 404."

Result<Integer, String> parsed = Numbers.tryInt(input).isPresent()
        ? Result.success(Numbers.tryInt(input).getAsInt())
        : Result.failure("not a number: " + input);

parsed.isSuccess();
parsed.isFailure();
parsed.get();                        // throws NoSuchElementException if failure
parsed.getError();                   // throws NoSuchElementException if success
parsed.orElse(0);
parsed.orElseGet(err -> -1);
parsed.orElseThrow(IllegalStateException::new);

parsed.map(n -> n * 2);              // transforms success, passes failure through
parsed.mapError(String::toUpperCase);
parsed.flatMap(n -> otherResult);

parsed.ifSuccess(n -> System.out.println("got " + n));
parsed.ifFailure(err -> System.out.println("failed: " + err));

parsed.toOptional();                 // Optional<T>, discards the error on failure

Wrapping a throwing call

Result<String, Exception> attempt = Result.of(() -> Files.readString(path));

Result.of catches any Exception thrown by the supplier and wraps it as a failure; a returned value becomes a success.

Deliberately small: Result covers success/failure, transformation, and extraction. It is not a general functional- programming toolkit — for anything more elaborate, use a Stream or Optional directly.

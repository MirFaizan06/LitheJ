Concurrent

Leak-proof structured concurrency for virtual threads, built entirely on Java 21's stable APIs — not the JDK's own preview StructuredTaskScope. Requires Java 21+; ships as its own opt-in artifact, lithej-concurrent, not part of the lithej aggregate.

Why this module is different from the rest of LitheJ: most of the library is a thin, honest layer over JDK APIs that are already simple. This one closes a real, current gap instead: the JDK's own structured-concurrency API has stayed in preview through every release since virtual threads went stable in JDK 21, so there has been no stable way to get its actual safety benefit — making a leaked background thread structurally impossible — without depending on an API whose shape keeps changing between JDK versions.

Basic usage

try (TaskScope scope = Concurrency.scope()) {
    Subtask<User> user = scope.fork(() -> fetchUser(id));
    Subtask<List<Order>> orders = scope.fork(() -> fetchOrders(id));

    scope.joinAll(); // waits for both; first failure cancels the other

    return new Profile(user.get(), orders.get());
} // guarantee: no forked task can outlive this block. Ever. Not "usually."

The guarantee

close() always waits for every forked task to actually finish before returning — whether or not joinAll() was ever called, and whether the try block exits normally, via an exception, or without ever reaching joinAll() at all. There is no equivalent guarantee from a hand-managed ExecutorService plus a list of Futures: forgetting one future.get() silently leaks a thread. Forgetting joinAll() here does not — close() performs the same failure check itself and throws, so a task failure is never silently swallowed either.

Failure policies

Concurrency.scope();                          // FailurePolicy.FAIL_FAST (default)
Concurrency.scope(FailurePolicy.COLLECT_ALL); // wait for everything, report every failure

FAIL_FAST (default): the first task failure immediately interrupts every other still-running task in the scope; joinAll() throws TaskFailedException wrapping that first failure once every task has actually finished.

try (TaskScope scope = Concurrency.scope()) {
    scope.fork(() -> riskyCall());
    scope.fork(() -> anotherRiskyCall());
    scope.joinAll(); // throws TaskFailedException if either failed
} catch (TaskFailedException e) {
    log.error("a task failed", e.getCause());
}

COLLECT_ALL: no task is cancelled because another failed; joinAll() waits for every task, then throws MultipleTaskFailuresException listing every failure (in fork order) if at least one failed.

try (TaskScope scope = Concurrency.scope(FailurePolicy.COLLECT_ALL)) {
    List<Subtask<Report>> reports = ids.stream().map(id -> scope.fork(() -> generate(id))).toList();
    try {
        scope.joinAll();
    } catch (MultipleTaskFailuresException e) {
        e.failures().forEach(f -> log.warn("report generation failed", f));
    }
    List<Report> succeeded = reports.stream()
            .filter(r -> r.state() == Subtask.State.SUCCESS)
            .map(Subtask::get)
            .toList();
}

Subtask states

A Subtask<T> (returned by fork()) moves from RUNNING to exactly one final state: SUCCESS, FAILED, or CANCELLED (interrupted as a result of a sibling's failure under FAIL_FAST — not counted as a failure by joinAll()). get()/exception() are only meaningful after the owning scope has joined.

Pinning diagnostics

While a scope has at least one forked task, it listens for jdk.VirtualThreadPinned JFR events — zero configuration, no JVM flags, no separate profiling run.

TaskScope scope = Concurrency.scope();
try {
    scope.fork(() -> riskyLegacyCodeThatMightStillUseSynchronized());
    scope.joinAll();
} finally {
    scope.close(); // this is what flushes JFR's buffered events
}
scope.pinningEvents().forEach(e ->
        log.warn("virtual thread pinned for {} at {}", e.duration(), e.stackTraceSummary()));
JDK 24 changed what "pinning" means. JEP 491 (JDK 24) changed synchronized so it generally no longer pins a blocked virtual thread at all. The diagnostic mechanism here is unaffected by that change — it still reports whatever pinning genuinely occurs (e.g. a blocking native/JNI call) — but on JDK 24+ you should expect far fewer pinning events for code written assuming synchronized pins. LitheJ's own test suite verifies both eras explicitly rather than assuming one.

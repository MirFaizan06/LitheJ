Async

Ergonomic helpers around CompletableFuture, from lithej-async. Every method either takes an explicit Executor or is clearly documented as using ForkJoinPool.commonPool() — the same default CompletableFuture.supplyAsync already uses. Nothing here silently creates an unbounded thread pool.

Running work

CompletableFuture<Integer> a = Async.run(() -> expensiveComputation());          // common pool — bold-documented
CompletableFuture<Integer> b = Async.run(() -> expensiveComputation(), myExecutor); // recommended: explicit executor
CompletableFuture<Void> c = Async.runAsync(() -> sideEffect(), myExecutor);         // no implicit-pool overload

Combining futures

CompletableFuture<List<Integer>> all = Async.all(listOfFutures);   // waits for all; fails if any fails
CompletableFuture<Integer> first = Async.anyOf(listOfFutures);     // first to complete, success OR failure

Blocking with a timeout

int value = Async.await(future, Duration.ofSeconds(5));

Translates the checked ExecutionException/InterruptedException/ TimeoutException that raw CompletableFuture.get(timeout, unit) would force you to handle into a small, consistent unchecked pair: AsyncExecutionException and AsyncTimeoutException.

Non-blocking timeout

CompletableFuture<Integer> withDeadline = Async.withTimeout(future, Duration.ofSeconds(5));
Note on mutation: withTimeout is built on CompletableFuture#orTimeout, which affects the same future object passed in, not a copy. If the timeout elapses, any other code holding a reference to the original future also observes an exceptional completion (with the JDK's own TimeoutException) — only the future returned by withTimeout translates that into AsyncTimeoutException. This is documented accurately rather than glossed over, since it's the kind of detail that causes confusing bugs if assumed otherwise.
